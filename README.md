# LLM Fine-Tuning Pipeline with LoRA/QLoRA

An end-to-end, reproducible pipeline for parameter-efficient fine-tuning
(PEFT) of a small open-source causal LM (1B–7B params) using LoRA/QLoRA,
the Hugging Face ecosystem (`transformers`, `peft`, `trl`, `datasets`,
`bitsandbytes`), and local experiment tracking via TensorBoard.

Built and verified to run on a **typical Windows machine with Docker
Desktop and a single consumer NVIDIA GPU** (e.g. RTX 30xx/40xx, 8–24GB
VRAM). Mixed precision (bf16 vs fp16) is auto-detected at runtime — no
YAML editing required regardless of which GPU generation you have.

Two execution paths are supported (see "Execution Options" below):

- **Docker** — the primary, fully reproducible workflow for anyone with
  an NVIDIA GPU (local or evaluator machine).
- **Google Colab** — `notebooks/colab_train.ipynb` runs the identical
  pipeline for anyone without a local NVIDIA GPU, using Colab's free GPU
  runtime.

### Data flow

```
HF Hub dataset
   │  data_pipeline.py (formats with the base model's OWN chat template)
   ▼
train/val/test split (80/10/10), each row: {text, prompt, target}
   │
   ├──────────────► train.py ──► 4-bit base model + LoRA adapters
   │                              │  SFTTrainer.train() (TensorBoard logging)
   │                              ▼
   │                 outputs/final_adapter/ (adapter_config.json,
   │                 adapter_model.safetensors)
   │
   └──────────────► evaluate.py ──► base model generations
                                 ──► base + LoRA adapter generations
                                     │  ROUGE comparison
                                     ▼
                          evaluation_report.md (auto-generated)
```

## Why LoRA / QLoRA

Full fine-tuning of a 7B model requires storing weights, gradients, and
optimizer states in full precision — on the order of hundreds of GB of
VRAM. LoRA freezes the pre-trained weights `W` and learns a low-rank
update `ΔW = BA` (with rank `r ≪ d, k`), reducing trainable parameters by
orders of magnitude. QLoRA goes further by loading the frozen base model
in 4-bit NormalFloat (NF4) precision with double quantization, while
keeping the LoRA adapters in 16-bit — enabling multi-billion-parameter
fine-tuning on a single consumer GPU.

## Model choice: `microsoft/Phi-3-mini-4k-instruct`

Of the three candidate models suggested by the assignment, Phi-3-mini is
kept as the default because it's the most reliable choice for this exact
setup (Windows + Docker Desktop + one consumer GPU):

| | Phi-3-mini-4k-instruct | Mistral-7B-v0.1 | Gemma-2b-it |
|---|---|---|---|
| Params | 3.8B | 7B | 2B |
| Gated (needs HF auth/license) | **No** | No | **Yes** |
| Already instruction-tuned | **Yes** | No (base model) | Yes |
| Approx. 4-bit VRAM footprint | ~3GB | ~5GB | ~2GB |

Mistral-7B-v0.1 is the *base* (non-chat) model, so SFT has to teach it
instruction-following from scratch — a much bigger lift on 1k+ examples.
Gemma requires accepting a license and an authenticated HF token before
the very first download, adding friction. Phi-3-mini needs neither, fits
comfortably in 4-bit on 6–8GB+ VRAM, and starts from an already
instruction-tuned checkpoint, so LoRA only has to specialize it rather
than teach it to follow instructions at all.

**Caveat:** Phi-3 ships custom modeling code in its own Hub repo, but that
code predates transformers' current RoPE config format and raises
`KeyError('type')` on `transformers>=5`. `transformers` has shipped Phi-3
natively since 4.41, so this repo sets `trust_remote_code: false` and
lets transformers use its own built-in implementation instead — already
handled by this repo's config and `requirements.txt`. If you swap in a
different model with no `chat_template` defined (e.g. a raw base model),
`data_pipeline.py` automatically falls back to a generic ChatML format —
see the "Swapping in a different model" section below.

## Execution Options

### Option A: Docker (NVIDIA GPU required)

The primary, fully reproducible workflow — use this if you (or the
evaluator) have a local NVIDIA GPU.

**Prerequisites (Windows)**

- **Docker Desktop**, set to the **WSL2 backend** (Settings → General →
  "Use the WSL 2 based engine").
- A **current NVIDIA driver installed on the Windows host** (not inside
  WSL — the WSL2 GPU passthrough uses the host driver). Get it from
  [nvidia.com/drivers](https://www.nvidia.com/Download/index.aspx).
- An NVIDIA GPU with ≥8GB VRAM (12GB+ recommended for comfortable batch
  sizes).
- At least ~20GB free disk space — the NVIDIA PyTorch base image alone is
  several GB, plus model weights and checkpoints.
- A Hugging Face account (free) — only strictly required if you swap in a
  gated model; not needed for the default Phi-3-mini.

**Verify GPU passthrough before doing anything else:**

```powershell
docker run --rm --gpus all nvidia/cuda:12.2.0-base-ubuntu22.04 nvidia-smi
```

This must print your GPU's name and driver version. If it fails, fix
Docker Desktop's GPU setup before proceeding — nothing below will work
without this.

**Setup**

1. **Clone and configure secrets**

   ```powershell
   git clone <your-repo-url>
   cd llm-finetuning-pipeline
   Copy-Item .env.example .env
   # Edit .env — the default Phi-3-mini model needs no token, so this
   # step is optional unless you plan to use a gated model.
   ```

2. **Build and enter the container**

   ```powershell
   docker compose build
   docker compose run --rm llm_tuner
   ```

   This drops you into a bash shell inside `/workspace`, with the CUDA
   runtime, PyTorch, and every pinned dependency from `requirements.txt`
   already installed. Continue with "Reproducing the Pipeline" below,
   running each command inside this shell.

### Option B: Google Colab (no NVIDIA GPU required)

For anyone without a local NVIDIA GPU. Runs the identical pipeline via
`notebooks/colab_train.ipynb` on Colab's free GPU runtime.

1. Upload `notebooks/colab_train.ipynb` to [Google Colab](https://colab.research.google.com/),
   or open it directly from GitHub once the repo is pushed.
2. **Runtime → Change runtime type → GPU**, then run cells top to bottom.
3. The notebook clones/updates the repo, installs and verifies
   dependencies, authenticates to Hugging Face (Colab Secrets or a
   hidden prompt — never typed in plaintext), and runs the exact same
   `data_pipeline.py` → `train.py` → `evaluate.py` steps described below,
   plus a 20-step smoke test before the full run.
4. TensorBoard launches inline in the notebook.
5. The last cell zips `outputs/final_adapter`, `outputs/eval_results`,
   the TensorBoard logs, and `evaluation_report.md`, and downloads the
   archive automatically.

Rerunning cells is safe: the notebook skips cloning if the repo already
exists (pulls instead), skips reinstalling dependencies that already
match `requirements.txt`, and skips training/evaluation if outputs are
already present (set `FORCE_RETRAIN` / `FORCE_REEVAL` in the first cell
to redo them).

## Reproducing the Pipeline

The commands below are identical in both workflows — inside the Docker
container shell (Option A, step 2), or as the notebook cells already
wired up for you in `colab_train.ipynb` (Option B). They use
`python -m src.<script>`, not `python src/<script>.py` (see "Why `-m`?"
below), run from the project root (`/workspace` in Docker,
`/content/llm-finetuning-pipeline` in Colab).

### 1. Prepare the dataset

```bash
python -m src.data_pipeline --config configs/training_config.yaml
```

Downloads the dataset named in `configs/training_config.yaml`
(`databricks/databricks-dolly-15k` by default, 15k+ examples), formats
every example using the **base model's own chat template** (not a
hardcoded generic one — see "Data formatting" below), drops any example
that exceeds `max_seq_length` (2048 tokens by default), and writes
`data/processed/{train,validation,test}.jsonl` using an 80/10/10 split.

### 2. Run training

```bash
python -m src.train --config configs/training_config.yaml
```

Loads the base model in 4-bit NF4 precision (mixed-precision dtype
auto-detected for your GPU), injects LoRA adapters on the attention
projections, and fine-tunes with `trl.SFTTrainer`. Checkpoints are
written to `outputs/checkpoints/` every `save_steps`; the final adapter
is saved to `outputs/final_adapter/`.

Any hyperparameter can be overridden from the command line without
editing the YAML:

```bash
python -m src.train --config configs/training_config.yaml \
    --learning_rate 1e-4 --lora_r 32 --num_epochs 2
```

With no flags, every setting comes purely from `training_config.yaml`.

**Tracking (TensorBoard, fully local — no account needed):**

```bash
tensorboard --logdir outputs/checkpoints/runs --host 0.0.0.0
```

`--host 0.0.0.0` is required to view the dashboard from outside the
container. To reach it from your Windows browser, run this in a
**second** shell into the same container with the port published:

```powershell
docker compose run --rm -p 6006:6006 llm_tuner tensorboard --logdir outputs/checkpoints/runs --host 0.0.0.0
```

Then open `http://localhost:6006`.

### 3. Evaluate

```bash
python -m src.evaluate --config configs/training_config.yaml
```

Loads the held-out `test.jsonl` split (never seen during training),
generates responses with **both** the frozen base model and the base
model + trained LoRA adapter, computes ROUGE for each, and saves:

- `outputs/eval_results/metrics.json` — quantitative base-vs-tuned scores
- `outputs/eval_results/qualitative_examples.json` — side-by-side generations
- **`evaluation_report.md`** — automatically generated from the above if
  it doesn't already exist (existing reports are never overwritten — delete
  it first if you want a fresh one). Fill in the `<...>` analysis
  placeholders it leaves for your own commentary.

### 4. (Optional) Merge adapters for deployment

```python
from src.model_utils import merge_and_save

merge_and_save(
    base_model_id="microsoft/Phi-3-mini-4k-instruct",
    adapter_path="outputs/final_adapter",
    output_dir="outputs/merged_model",
)
```

Produces a single standalone model directory for serving with
`transformers`/`vLLM`/TGI.

## Why `-m`, not `python src/<script>.py`?

Running scripts as modules (`python -m src.train` from `/workspace`)
rather than directly (`python src/train.py`) matters here for a subtle
but real reason: `src/evaluate.py` imports the Hugging Face `evaluate`
package. If you ran it directly, Python would put `src/` — which contains
a file literally named `evaluate.py` — at the front of `sys.path`, and
`import evaluate` would import *itself* instead of the real package,
crashing with `AttributeError: module 'evaluate' has no attribute
'load'`. Running as `-m` from the project root avoids this entirely and
is used consistently across all three scripts for the same reason.

## Data formatting

`data_pipeline.py` formats every example with
`tokenizer.apply_chat_template(...)`, i.e. whatever turn-delimiter tokens
the configured base model actually understands (Phi-3 uses
`<|user|>`/`<|assistant|>`/`<|end|>`, not literal `<|im_start|>`/`<|im_end|>`
ChatML tags). Hardcoding generic ChatML tags for a model that wasn't
trained on them causes the tags to be split into ordinary subwords instead
of atomic turn markers — a common cause of the model never learning its
real end-of-turn token, leading to endless/repetitive generation at
inference time. If you swap in a base (non-instruct) model with no chat
template defined, formatting automatically falls back to a generic
ChatML template.

Each saved row has three fields: `text` (full conversation, used for
training), `prompt` (conversation up to the generation point, no
response — used by `evaluate.py`), and `target` (the raw ground-truth
response — used as the ROUGE reference).

## Configuration Reference

All hyperparameters live in `configs/training_config.yaml`:

| Section | Key | Purpose |
|---|---|---|
| `dataset` | `name_or_path`, `max_seq_length`, splits | Data source and preprocessing |
| `model` | `base_model_id` | Which 1B–7B base model to fine-tune |
| `quantization` | `load_in_4bit`, `bnb_4bit_compute_dtype: "auto"` | QLoRA 4-bit settings; compute dtype auto-detected per-GPU |
| `lora` | `r`, `lora_alpha`, `target_modules` | Adapter capacity and placement |
| `training` | `learning_rate`, `per_device_train_batch_size`, `gradient_accumulation_steps`, `precision: "auto"`, `report_to: "tensorboard"` | Training loop + local tracking |
| `evaluation` | `max_new_tokens`, `metrics`, `report_path` | Evaluation behavior + auto-generated report path |

`precision: "auto"` and `bnb_4bit_compute_dtype: "auto"` both resolve at
runtime via `torch.cuda.is_bf16_supported()` — bf16 on Ampere/Ada/Hopper
GPUs (RTX 30xx/40xx and newer), fp16 automatically on everything older
(GTX 16xx, RTX 20xx). You can still set either to an explicit value; an
unsupported choice (e.g. forcing `bfloat16` on an RTX 2080) is
auto-corrected to `float16` with a logged warning rather than failing.

## Swapping in a different model

Change `model.base_model_id` in the config. If it's gated (Llama, Gemma,
some Mistral variants), accept the license on its Hugging Face model page
and set `HUGGING_FACE_HUB_TOKEN` in `.env`. Everything else — chat
template formatting, precision detection, quantization — adapts
automatically.

## Troubleshooting

**`ModuleNotFoundError: No module named 'liger_kernel'` or `'triton.ops'`
during `from trl import SFTTrainer` / `bitsandbytes` import** — these come
from old, no-longer-mutually-compatible pins (`trl==0.9.6`,
`bitsandbytes==0.43.1`) fighting a modern torch build. `requirements.txt`
is pinned to a verified-compatible set (`transformers==5.14.1`,
`trl==1.9.2`, `peft==0.20.0`, `accelerate==1.14.0`,
`bitsandbytes==0.50.0`) — if you still hit this, you likely have a stale
environment: rebuild the Docker image (`docker compose build --no-cache`)
or, in Colab, `Runtime → Restart session` before re-running the
dependency cell so old wheels aren't left on `sys.path`.

**`KeyError: 'type'` in `modeling_phi3.py`, at `self.config.rope_scaling["type"]`**
— Phi-3's Hub repo ships its own `modeling_phi3.py`/`configuration_phi3.py`,
written before transformers standardized `rope_scaling` on a `"rope_type"`
key. With `trust_remote_code: true`, that stale repo code runs against a
config normalized by the *current* transformers, and the key it expects
isn't there. Fix: `model.trust_remote_code: false` in the config (already
set) — transformers has shipped Phi-3 natively since 4.41, and the
built-in implementation matches its own config normalization. This is not
a downloaded-file patch; it just tells `AutoModelForCausalLM` to use the
library's own class instead of fetching the repo's copy.

**CUDA Out of Memory (OOM)** — confirm `quantization.load_in_4bit: true`
is set, drop `training.per_device_train_batch_size` to `1` and raise
`gradient_accumulation_steps` to compensate, and check that
`dataset.max_seq_length` isn't set too high for your GPU's VRAM. Every
script here raises a specific `RuntimeError` with these suggestions if a
CUDA OOM is caught.

**"No CUDA GPU is visible"** — the exact fix depends on where you're
running:
- **Colab:** Runtime → Change runtime type → GPU, then Runtime → Restart
  session.
- **Docker:** GPU passthrough isn't working. Re-run the verification
  command from the Option A Prerequisites above; if it fails, check
  Docker Desktop → Settings → General is on the WSL2 backend, and that
  your Windows NVIDIA driver is current.
- **Local (no Docker/Colab):** confirm `nvidia-smi` runs and your driver
  is current.

**Loss is flat or drops to zero immediately** — usually a data-formatting
bug. Decode a tokenized training example just before it enters the
trainer and manually inspect it; also confirm `lora.target_modules`
actually match layer names in your chosen base model
(`apply_lora_adapters` logs a warning if zero parameters end up
trainable).

**Generation never stops / repeats endlessly** — as of this version,
formatting uses the model's own chat template specifically to avoid this
(see "Data formatting" above). If you still see it after swapping models,
confirm the new model's tokenizer actually defines `eos_token` and that
its `chat_template` is not `None`.

**`docker compose build` fails on `env_file: .env`** — you skipped step 1
of Setup. Run `Copy-Item .env.example .env` first; Compose requires the
referenced file to exist even if every value in it is left as a default.

**Build or first run feels very slow** — the NVIDIA PyTorch base image is
several GB; this is a one-time cost. If your machine has limited RAM, WSL2
may need more memory allocated via a `.wslconfig` file — see
[Microsoft's WSL config docs](https://learn.microsoft.com/en-us/windows/wsl/wsl-config).
